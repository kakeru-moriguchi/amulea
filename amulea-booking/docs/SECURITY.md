# セキュリティ方針

このシステムはお客様の**お名前・電話番号・来店予定**という
個人情報を扱います。実装した対策と、その理由をまとめます。

---

## 1. 認証情報（APIキー・秘密鍵）

| 要件 | 実装 |
| --- | --- |
| ソースコードへ直書きしない | すべて環境変数。読み込み口は `lib/config/env.ts` の1か所のみ |
| `.env` を Git 管理外にする | `.gitignore` で `.env*` を除外（`.env.example` のみ例外） |
| LINE Channel Secret をフロントへ出さない | そもそも使用していません（IDトークン検証で足りるため） |
| LINE アクセストークンをフロントへ出さない | サーバー専用。`lib/line/messaging.ts` からのみ参照 |
| Google 秘密鍵をフロントへ出さない | サーバー専用。`lib/google/auth.ts` からのみ参照 |

### ブラウザへ渡している値

Next.js では `NEXT_PUBLIC_` が付いた環境変数だけがブラウザへ渡ります。
このシステムで該当するのは **`NEXT_PUBLIC_LIFF_ID` の1つだけ**です。

LIFF ID は公開前提の値で、これ単体では何もできません。
（LINE 公式のドキュメントでも公開してよい値とされています）

---

## 2. 他人の予約を見せない

**もっとも重要な要件です。** 三重に守っています。

### ① セッションから userId を取る

```
リクエストのボディに userId が入っていても、完全に無視します。
```

必ず `requireCustomer()` が署名付きCookieから取り出した値を使います
（`lib/api/http.ts`）。

### ② サーバー側で一致を確認する

```ts
// lib/domain/booking.ts
if (found.lineUserId !== lineUserId) return null;
```

URLの予約IDを書き換えても、他人の予約は取得できません。

### ③ 「権限がありません」ではなく「見つかりません」を返す

予約IDが**存在するかどうか**を外部から探れないようにするためです。
（存在すれば403、しなければ404、では情報が漏れます）

### 実際に確認済みの動作

| 操作 | 結果 |
| --- | --- |
| 他人の予約IDで GET | `404 予約が見つかりませんでした。` |
| 他人の予約IDで PATCH（変更） | `403 この予約を操作する権限がありません。` |
| 他人の予約IDで キャンセル | `403 この予約を操作する権限がありません。` |
| 別ユーザーのマイ予約一覧 | 空（他人の予約は1件も混ざらない） |

---

## 3. LINE の誤送信防止

「Aさんの予約内容がBさんに届く」ことは、絶対に起こしてはいけません。

| 要件 | 実装 |
| --- | --- |
| userId はサーバー側で取得 | LINE のサーバーへIDトークンを送り、返ってきた `sub` のみ使用 |
| クライアントから userId を指定させない | リクエストの userId は読み取りません |
| 保存済みの userId だけを通知先にする | `notifyCustomer(reservationId, reservation.lineUserId, ...)` |
| 名前・電話番号から推測しない | そのような処理は存在しません |
| 予約変更時に userId を変えない | 変更処理は `{...before}` を展開するため、`lineUserId` は必ず引き継がれます |
| 通知直前に紐付きを確認 | 通知に渡すのは予約レコードから読み出した値のみ。形式（`U`+32文字）も検証 |

管理者が電話で受けた予約は `lineUserId` が空になります。
このとき**通知は送られません**（宛先が分からないため）。
名前が同じ別のお客様へ誤送信することを防いでいます。

---

## 4. 管理者の保護

| 対策 | 実装 |
| --- | --- |
| すべての管理APIで認証 | `/api/admin/*` の全ルートで `requireAdmin()` を実行 |
| パスワードを平文で保存しない | scrypt でハッシュ化（`scripts/hash-password.mjs` で生成） |
| 総当たり対策 | ログインは5分あたり10回まで |
| どちらが違うか教えない | IDが違ってもパスワードが違っても同じメッセージ |
| タイミング攻撃対策 | `timingSafeEqual` で比較 |
| セッションを短くする | 管理者は12時間で自動ログアウト |

> 画面の `/admin` へのアクセス制限は「入口の案内」にすぎません。
> **本当の防御はAPI側**にあります。画面を迂回してAPIを直接叩いても、
> 管理者セッションがなければ 401 が返ります。

## 5. Web の一般的な攻撃への対策

### XSS（悪意あるスクリプトの埋め込み）

- React が文字列を自動でエスケープします
- **`dangerouslySetInnerHTML` を一切使用していません**
- 保存前に制御文字を除去します（`lib/security/validation.ts`）
- CSP（Content-Security-Policy）で外部スクリプトの実行元を限定

### CSRF（罠サイトから勝手に操作される）

三重に防いでいます。

1. Cookie の `SameSite=Lax` — 他サイトからのPOSTでCookieが送られない
2. `Origin` / `Referer` の検証 — 自サイト以外からのリクエストを拒否
3. `Content-Type: application/json` の必須化 — HTMLフォームからは送れない形式

### インジェクション

- SQL を使用していないため、SQLインジェクションは発生しません
- スプレッドシート特有の**数式インジェクション**
  （`=` や `+` で始まる入力がセルで数式として実行される問題）は、
  `sanitizeForSheet()` で先頭にアポストロフィを付けて無害化しています

### クリックジャッキング

`X-Frame-Options: DENY` と CSP の `frame-ancestors 'none'` で
他サイトの iframe への埋め込みを禁止しています。

### レート制限

| 対象 | 制限 |
| --- | --- |
| 予約の作成・変更・キャンセル | 60秒あたり20回 |
| 管理者ログイン | 300秒あたり10回 |
| 空き時間の取得など読み取り | 60秒あたり120回 |

> Vercel はサーバーを複数に分けるため、この制限は厳密ではありません。
> 素朴な連打や簡易な攻撃を防ぐためのものです。
> より厳密にしたい場合は `lib/security/rate-limit.ts` を
> Vercel KV / Upstash Redis に差し替えてください。

## 6. 個人情報を残さない場所

| 場所 | 載せているもの | 載せていないもの |
| --- | --- | --- |
| URL | 予約ID（UUID）のみ | 名前・電話番号・メニュー |
| Google カレンダー | メニュー名・予約ID | **氏名・電話番号・自由記載** |
| LINE通知（お客様） | 日時・メニュー・料金 | 電話番号・自由記載 |
| LINE通知（管理者） | 日時・メニュー・氏名 | 電話番号・自由記載 |
| サーバーログ | 予約IDの先頭8文字、userIdの短縮形 | **電話番号・自由記載・氏名** |
| APIレスポンス | 画面に必要な項目のみ | LINE userId、カレンダーのイベントID |

### 予約IDについて

連番だと「1つ増やせば他人の予約が見える」状態になりかねないため、
**UUID v4**（推測が事実上不可能）を使用しています。
加えて、前述のとおりサーバー側でも本人確認を行っています。

### Referrer 制御

予約IDがURLに含まれるため、外部サイトへ `Referer` として
漏れないよう `Referrer-Policy: same-origin` を設定しています。

## 7. エラーメッセージ

例外の内容をそのままクライアントへ返しません。

```ts
// lib/api/http.ts
catch (e) {
  log.error(`API エラー: ${label}`, e);   // 詳細はサーバーのログだけ
  return error(500, "処理中に問題が発生しました。時間をおいてお試しください。");
}
```

Google API のエラーも、**応答本文を残しません**。
「どのAPIが」「HTTP何番で」失敗したかだけを記録します。

## 8. 送信されるHTTPヘッダー

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline'
  https://static.line-scdn.net; ... ; frame-ancestors 'none'; object-src 'none'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: same-origin
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Cache-Control: no-store, max-age=0        （/api/* のみ）
```

`x-powered-by` ヘッダーは削除しています。

### `'unsafe-inline'` について（正直に書きます）

CSP の `script-src` に `'unsafe-inline'` を含めています。
Next.js が画面の初期表示のためにインラインの `<script>` を出力するためで、
これを禁止するとアプリが動きません。

そのぶん、**XSS そのものを起こさない対策**を徹底しています
（React の自動エスケープ、`dangerouslySetInnerHTML` 不使用、制御文字の除去）。

より厳格にしたい場合は、Next.js の Middleware で
リクエストごとに nonce を発行する方式へ移行できます。

## 9. 運用でお願いしたいこと

| いつ | やること |
| --- | --- |
| 公開前 | `MOCK_MODE=false` にする |
| 公開前 | `SESSION_SECRET` と `ADMIN_PASSWORD_HASH` を必ず設定する |
| 公開前 | ダウンロードしたGoogleの鍵ファイル（JSON）をパソコンから削除する |
| 定期的に | 管理者パスワードを変更する |
| 鍵が漏れたら | LINE: トークンを再発行 / Google: 鍵を削除して作り直す |
| 退職者が出たら | `SESSION_SECRET` を変更する（全員がログアウトされます） |

### 絶対にやってはいけないこと

- `.env.local` を GitHub にアップロードする
- Google の鍵ファイル（JSON）をメールやチャットで送る
- LINE のチャネルアクセストークンを誰かに教える
- `MOCK_MODE=true` のまま本番公開する（データが消えます）

## 10. 既知の限界

正直にお伝えしておきます。

1. **二重予約の防止は「ほぼ確実」であって「絶対」ではありません。**
   Google カレンダーの検索結果には、ごくまれに反映の遅れが起こり得ます。
   お一人で運営されるサロンの予約頻度では実用上の問題はありませんが、
   厳密さが必要になった場合はデータベースへの移行をおすすめします
   （`docs/ARCHITECTURE.md` の「8. 予約競合防止方法」を参照）。

2. **レート制限はサーバー単位です。**
   Vercel が複数のサーバーに分かれると、制限が緩くなります。

3. **お客様の本人確認は LINE アカウントに依存します。**
   LINE アカウントを乗っ取られた場合、その方の予約は操作されてしまいます。
   これは LINE を使う以上、避けられない性質です。
