## 1. 推奨アーキテクチャ

### 採用した構成

| 層 | 採用技術 | 理由 |
| --- | --- | --- |
| フロント | Next.js 16（App Router）+ TypeScript | Vercel へそのままデプロイでき、既存ホームページと同じ技術のため保守しやすい |
| デザイン | Tailwind CSS v4 | 既存ホームページと同じ。ブランドカラーの定義をそのまま持ち込める |
| サーバー | Next.js Route Handlers（`app/api/`） | フロントと同じプロジェクトで完結し、デプロイ先が1つで済む |
| 予定管理 | Google Calendar API | 空き判定の「正」。管理者の私用予定も自動で予約不可にできる |
| データ保存 | Google Sheets API | サロン側が普段の道具で予約を確認・バックアップできる |
| 通知 | LINE Messaging API | お客様も管理者も、普段使っている LINE で受け取れる |
| 本人確認 | LINE Login（LIFF） | お客様が ID・パスワードを覚える必要がない |

### Google Apps Script を採用しなかった理由

ご依頼で「GAS を使った方がシンプルなら採用してよい」とありましたが、
**採用していません**。理由は次の3点です。

1. **二重予約防止が難しい** — GAS の同時実行制御（LockService）は
   実行時間の上限が短く、予約が混み合うタイミングで詰まる恐れがあります。
2. **秘密情報の管理が分散する** — Vercel と GAS の2か所に認証情報を
   置くことになり、「どこに何があるか」が分かりにくくなります。
3. **保守の窓口が2つになる** — 障害調査のときに見る場所が増えます。

Next.js の Route Handlers に集約したほうが、
**セキュリティ・保守性・二重予約防止**のすべてで有利と判断しました。

### なぜ「Google カレンダーが正、スプレッドシートが記録」なのか

- カレンダーは **管理者が普段使うもの**です。
  ここに私用の予定を入れるだけで自動的に予約不可にできます。
- スプレッドシートは **一覧性・検索性・バックアップ**に優れます。
  ただし同時書き込みの排他制御を持たないため、
  「どちらが先に予約したか」の判定には使えません。

そこで **空き判定と二重予約防止はカレンダー、詳細記録はシート**
という役割分担にしています。

## 3. データ構造

### 予約（Reservation）

| 項目 | 型 | 説明 |
| --- | --- | --- |
| `id` | UUID | 推測されにくいID。URLに載るため連番にしない |
| `lineUserId` | string | ★ 本人確認と通知先の判定に使う唯一の値 |
| `customerName` / `phone` | string | お名前・電話番号 |
| `menuId` / `menuName` / `menuPrice` / `menuDurationMin` | - | **予約時点の内容を保存**。後から料金を変えても過去の予約は変わらない |
| `optionIds` / `optionNames` / `optionPrice` | - | オプション |
| `totalDurationMin` / `totalPrice` | number | 合計時間・合計料金 |
| `date` / `startTime` / `endTime` | string | 施術の日時（日本時間） |
| `blockStartTime` / `blockEndTime` | string | **準備時間を含めて実際に押さえる枠** |
| `note` | string | 自由記載 |
| `status` | confirmed / cancelled | キャンセルは削除せず状態を変える（履歴が残る） |
| `source` | customer / admin | お客様の予約か、管理者の手動登録か |
| `googleCalendarEventId` | string \| null | カレンダーのイベントID |
| `createdAt` / `updatedAt` / `cancelledAt` | ISO日時 | 記録用 |

> **なぜメニュー名や料金を予約側にも保存するのか**
> メニューIDだけを保存すると、後日料金を変えたときに
> 過去の予約の金額まで変わってしまいます。
> 「そのとき何をいくらで予約したか」を残すため、値を複製しています。

### 営業設定（Settings）

営業時間（平日／土日祝）、予約枠の刻み、**前後の準備時間**、定休日、
臨時休業日、特別営業時間、予約受付停止の時間帯、受付期間、
変更・キャンセル期限、LINE通知のON/OFF を保持します。
すべて管理画面から変更でき、スプレッドシートに保存されます。

### メニュー・オプション

コードに固定していません。初期値は `lib/domain/defaults.ts` にありますが、
保存後は管理画面の内容が優先されます。
オプションには `extraDurationMin`（追加でかかる時間）があり、
たとえば「占い10分」を選ぶと予約枠が10分伸びます。

## 4. Google 連携方法

### 認証方式：サービスアカウント

お客様や管理者に Google ログインをさせません。
サーバーが「サービスアカウント」という専用のアカウントで
カレンダーとシートに直接アクセスします。

```
サーバー ──[秘密鍵で署名したJWT]──▶ Google
        ◀──[アクセストークン（1時間）]──
```

- 秘密鍵は環境変数からのみ読み込みます（`lib/config/env.ts`）
- トークンは有効期限まで使い回します（毎回取り直しません）
- 外部ライブラリ（googleapis）は使わず、Node 標準の `crypto` と
  `fetch` だけで実装しています（依存を減らし、挙動を追いやすくするため）

### カレンダーの使い方

**読むとき**（空き判定）
- 時間指定の予定 → その時間は予約不可
- **終日予定** → その日は丸ごと予約不可（「休業」と入れるだけで休みにできる）
- 「予定なし（transparent）」の予定 → 無視する

**書くとき**（予約確定時）
- タイトルは `Amulea予約｜極上リンパアロマトリートメント` のみ
- **氏名・電話番号・自由記載は書き込みません**
- 予約IDだけを説明欄と非公開プロパティに入れ、詳細は管理画面で見ます

## 5. LINE 連携方法

### LIFF + LINE Login + Messaging API の3点構成

| 用途 | 使うもの |
| --- | --- |
| お客様が誰かを知る | LIFF（LINE Login チャネル） |
| 予約完了・変更・キャンセルの通知 | Messaging API チャネル |

### なぜ LIFF なのか

お客様は公式LINEのリッチメニューから、LINEアプリ内のブラウザで開きます。
LIFF を使うと、その状態で「今LINEを使っているのが誰か」を
**お客様の操作なし**で安全に取得できます。

### 本人確認の流れ（ここが最重要）

```
ブラウザ ──[IDトークンだけ]──▶ 当アプリのサーバー
                                    │
                                    ├──[IDトークン]──▶ LINEのサーバー
                                    ◀──[userId（sub）]──
                                    │
                              ★ この userId だけを信用する
                                    │
                            署名付きCookieを発行
```

**ブラウザから userId を受け取ることは一切ありません。**
リクエストに userId が入っていても、サーバーは完全に無視します。

## 6. 認証方法

| 対象 | 方式 | 有効期間 |
| --- | --- | --- |
| お客様 | LINE IDトークン検証 → HMAC署名付きCookie | 30日 |
| 管理者 | ID + パスワード（scrypt ハッシュ） → 署名付きCookie | 12時間 |

Cookie の設定：

- `httpOnly` — JavaScript から読めない（XSSで盗まれない）
- `secure` — HTTPS でのみ送信（本番）
- `sameSite=lax` — 他サイトからのリクエストでは送られない
- **HMAC-SHA256 署名** — 中身を書き換えると検証に失敗する

管理者パスワードは平文で保存せず、scrypt でハッシュ化した値だけを
環境変数に置きます。比較は `timingSafeEqual` で行い、
応答時間からパスワードを推測されないようにしています。

## 7. セキュリティ方針

詳細は `docs/SECURITY.md` にまとめています。要点だけ挙げます。

| 対策 | 実装 |
| --- | --- |
| APIキーの直書き禁止 | すべて `lib/config/env.ts` 経由。`.env` は Git 管理外 |
| 秘密情報のフロント公開防止 | `NEXT_PUBLIC_` が付くのは LIFF ID のみ |
| 他人の予約の閲覧防止 | サーバー側で userId 一致を必ず確認。不一致は「見つかりません」を返す |
| 管理APIの認証 | すべての `/api/admin/*` で管理者セッションを検証 |
| 入力値の検証 | サーバー側で全項目を検証（フロントの検証は体験向上のみ） |
| XSS | React の自動エスケープ。`dangerouslySetInnerHTML` を一切使わない。CSPを設定 |
| CSRF | SameSite Cookie + Origin/Referer 検証 + JSON必須の三重 |
| インジェクション | SQLを使わない。スプレッドシートの数式インジェクションは無害化 |
| レート制限 | 予約・ログインAPIに回数制限。ログインは5分10回まで |
| ログ | 電話番号・自由記載を出力しない。userIdは短縮表示 |
| エラーメッセージ | 例外の中身をクライアントへ返さない |

## 8. 予約競合防止方法

**ここが最も重要な設計です。**

### なぜ難しいのか

Vercel はアクセスに応じてサーバーを複数に増やします。
そのため「サーバーのメモリ上で順番待ちさせる」だけでは不十分です。
別々のサーバーで動く2つのリクエストが、
同時に「空いている」と判断してしまう可能性があります。

### 解決策：カレンダーを使った楽観的ロック

予約確定時、次の順序で処理します。

```
1. 同一サーバー内の処理を1件ずつに直列化する（ロック）
        ↓
2. 空き時間をもう一度サーバー側で計算し直す
   （保存済み予約 + カレンダーの予定）
        ↓
3. ★ 先に Google カレンダーへイベントを作成して「場所を取る」
        ↓
4. ★ 作成した直後に、もう一度その時間帯を問い合わせる
        ↓
5. 自分以外の予定が重なっていたら、作ったイベントを消して失敗にする
```

### 「両方が諦めてしまう」問題への対処

2人が同時に予約すると、手順4でお互いのイベントを見つけ、
両方が譲ってしまう可能性があります。そこで勝敗の規則を決めています。

- 予約以外の予定（管理者の私用など）が重なっていたら → **必ず自分が譲る**
- 予約どうしがぶつかったら → **イベントIDが小さいほうが勝つ**

両者が同じ規則で判断するため、**必ず片方だけが成立します。**

### 失敗時の表示

```
申し訳ありません。この時間は先ほど他のお客様の予約が入りました。
別のお時間をお選びください。
```

このとき画面は自動的に「時間の選び直し」へ戻ります。

### 正直に書いておく限界

Google カレンダーの検索結果には、ごくまれに反映の遅れが起こり得ます。
確率は非常に低く、お一人で運営されるサロンの予約頻度であれば
実用上の問題はありませんが、**完全にゼロとは言い切れません**。

将来、予約数が大きく増えて厳密さが必要になった場合は、
データベース（Vercel Postgres など）に
「同じ時間帯には1件しか入れられない」制約を付けるのが確実です。
その差し替えができるよう、保存先は `lib/store/` の
インターフェース1つに閉じ込めてあります。

## 9. 実装順序

ご依頼の Phase 分けに沿って実装しました。
**Phase 1〜3 と、Phase 4 のうちコードで用意できる部分は完了しています。**

| Phase | 内容 | 状態 |
| --- | --- | --- |
| Phase 1 | UI・予約ロジック・管理画面（モックデータで動作） | ✅ 完了・動作確認済み |
| Phase 2 | Google カレンダー連携 | ✅ 実装済み（要：認証情報の設定） |
| Phase 3 | Google スプレッドシート連携 | ✅ 実装済み（要：認証情報の設定） |

| Phase 5 | 本番環境テスト | ⏳ 認証情報の設定後に実施 |

`MOCK_MODE=true` のあいだは Google も LINE も呼びません。
認証情報を設定して `MOCK_MODE=false` にすると、
**コードを一切変えずに**連携が有効になります。
